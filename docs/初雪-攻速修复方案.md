# 初雪「攻速」修复方案（DSH 任务单）

> 状态：已实施（2026-11-09）。对应问题记录见《初雪-自动攻击与攻速问题记录.md》。
> 结论先行：**放弃自动攻击（方案 C），只改 ComboState 的连段速度与时间窗口。**

---

## 0. 结论摘要

初雪的平 A 攻速由拔刀剑自己的 `ComboState` 状态机驱动，跟原版 `ATTACK_SPEED` 属性无关。真正卡住攻速的是三层东西，按重要性排序：

1. **分支窗口（branch window）** —— 连段之间"下一刀最早什么时候能接上"的最小间隔。**这是真正的限速器，之前的分析都漏了它。**
2. **`fastGround` 的 timeout 补偿** —— 把 `speed×2` 带来的动画缩短又补回了原值，总时长没变。
3. **`tick` 命中偏移不随 `speed` 移动** —— A3/A4/A5 的多段伤害仍落在原版固定 tick 上，动画快了伤害却没跟上。

`ATTACK_SPEED`、i-frame 清理、服务端直伤循环，都是错误路径，应当删除。

---

## 1. 根因（精确版）

### 根因 A：`ATTACK_SPEED` 用错地方

拔刀剑右键平 A 的链路（反编译 `ItemSlashBlade` / `ISlashBladeState` 得到）：

```
右键按下 → ItemSlashBlade.use()
        → state.progressCombo(player)      // 判断能否推进连段
        → updateComboSeq() → clickAction()  // 真正出刀
        → AttackManager.doSlash()          // 生成 EntitySlashEffect 斩击实体
        → EntitySlashEffect.tick()         // 每 2 tick 判一次命中并扣血
```

`use()` 每次右键按下只触发一次（按住走 `onUseTick` 蓄力，松开走 `releaseUsing` 放 SA）。整条链路不读 `ATTACK_SPEED`，所以 `FirstSnowSpeedHandler` 的 `+36` 只让 `/attribute` 显示 40.0，对右键连段零作用。

### 根因 B：分支窗口才是真正限速器（关键，ChatGPT 漏掉的部分）

`ISlashBladeState.progressCombo` 里：

```java
ResourceLocation next = event.getNextCombo();           // = current.getNext(user)
if (!next.equals(NONE) && next.equals(currentloc)) {
    return NONE;                                        // 点得太快 → 输入被丢弃，不出刀
}
```

`getNext` 默认是 `ComboState.TimeoutNext.buildFromFrame(N, nextState)`：

```java
public ResourceLocation apply(LivingEntity livingEntity) {
    long elapsed = ComboState.getElapsed(livingEntity); // 进入本段后的游戏 tick 数
    return this.timeout <= elapsed ? this.next.apply(...) : currentComboSeq;
}
```

其中 `timeout = getTicksFromFrames(N) = (int)(N × 2/3)`，**单位是游戏 tick，跟 `speed` 字段无关**。

原版地面连段的分支窗口：

| 连段 | buildFromFrame | 分支窗口 | 出刀方式 |
|---|---|---|---|
| combo_a1 → a2 | 5 帧 | **3 tick (150ms)** | clickAction 1 刀 |
| combo_a2 → a3 | 5 帧 | **3 tick** | clickAction 1 刀 |
| combo_a3 → a4 | 9 帧 | 6 tick | tick 2 / 6 各 1 刀 |
| combo_a4 → a5 | 21 帧 | 14 tick | tick 8 / 9 各 1 刀 |
| combo_a5 → 结束 | 33 帧 | 22 tick | tick 15 / 17 / 19 各 1 刀 |

实测 ~200ms = **3 tick 分支窗口 + 1 tick 输入/网络延迟**。这就是平 A 慢的直接原因。**只改 `speed` 或只修 timeout，分支窗口不动，节奏就永远卡在 3 tick。**

### 根因 C：`fastGround` 的 timeout 补偿抵消了 speed

`ModComboStates.fastGround` 当前：

```java
int fastActionMs = (int)(getMSecFromFrames(frames) / (original.getSpeed() * FAST_GROUND_SPEED)); // = 原动画时长 / 2
int timeout = Math.max(0, original.getTimeoutMS() - fastActionMs);                              // 补回差额
```

而 `ComboState.getTimeoutMS()` 的定义：

```
getTimeoutMS = getMSecFromFrames(frames) / speed + timeout
```

代入后 fast 状态的实际超时：

```
getTimeoutMS_new = 动画时长/2 + (原动画时长 + 原timeout - 动画时长/2) = 原动画时长 + 原timeout = getTimeoutMS_old
```

即 **`speed×2` 后 `getTimeoutMS` 与原版完全相等**。动画视觉快了一倍，状态总时长却一点没短。ChatGPT 指出了这一点，正确，但它是次要问题——即使修好它，分支窗口仍会卡 3 tick。

### 根因 D：tick 命中偏移不随 speed 移动

A3/A4/A5 的伤害写在 `TimeLineTickAction` 里，键是 `getElapsed` 的游戏 tick，不是 VMD 帧，`speed` 不影响它们。所以 `speed×2` 后，动画转完了，伤害却仍落在原版 tick（A3 的 2/6、A4 的 8/9、A5 的 15/17/19），动画与判定脱节。

### 附：实验性代码绕过连段系统

`FirstSnowHoldScheduler` 直接 `target.hurt(...)`，间隔 `max(1, ceil(20/ATTACK_SPEED))` 在 40.0 攻速下恒为 1 tick（50ms），这是"假伤害"，绕过了 ComboState、原生攻击、SA 语义和耐久处理，测出的 52ms 不能当作平 A 攻速。

## 2. 修复方案（方案 C：不做自动攻击）

### 阶段一：删除错误路径（先做，降低后续噪音）

| 类 / 文件 | 动作 | 说明 |
|---|---|---|
| `combat/FirstSnowSpeedHandler.java` | **删除** | `ATTACK_SPEED +36` 对右键连段无效 |
| `mixin/LivingEntityHurtMixin.java` | **删除** | i-frame 清理多余；`doSlash` 内部已 `forceHit=true` |
| `client/MistletoeAutoAttack.java` | **删除** | 监听左键，与"右键点按=平 A"语义冲突 |
| `network/FirstSnowHoldPayload.java` | **删除** | 按住状态网络包，实验性 |
| `network/FirstSnowHoldScheduler.java` | **删除** | 服务端直伤循环，非真正攻击 |
| `MistletoeDamage.onIncomingDamage` 里初雪段 | **删除** | `invulnerableTime=0` + `FIRST_SNOW_IFRAME_TARGETS` 兜底，多余 |

同时清理：`TerminalBlade` 构造器里 `FirstSnowHoldPayload` 的注册、`TerminalBladeClient` 里对 `MistletoeAutoAttack` 的引用、`MistletoeDamage` 里 `FIRST_SNOW_IFRAME_TARGETS` 及 `onServerTick` 里的清理逻辑。

### 阶段二：重做初雪快速连段

**目标**：初雪持有者用右键点按，A1→A2→A3 的出刀间隔从 150ms 降到 100ms（后续可到 50–100ms），动画与判定同步。

改 `ModComboStates.fastGround`，从"复制 speed 并委托原版 `next`"改成"自闭环短分支窗口连段"：

```java
private static ComboState fastGround(
        DeferredHolder<ComboState, ComboState> base,
        int branchFrames,                                              // 分支窗口（帧）
        Function<LivingEntity, ResourceLocation> fastNext) {           // 指向下一个 fast 段
    ComboState original = base.get();
    ComboState.Builder builder = ComboState.Builder.newInstance()
            .startAndEnd(original.getStartFrame(), original.getEndFrame())
            .priority(original.getPriority())
            .speed(original.getSpeed() * FAST_GROUND_SPEED)            // 只加速动画
            .motionLoc(original.getMotionLoc())
            // 关键 1：短分支窗口 + 直接指向下一个 fast 段（不再走 original.getNext 的 3-tick 窗口）
            .next(e -> ComboState.TimeoutNext.buildFromFrame(branchFrames, fastNext).apply(e))
            // 关键 2：timeout 归零，让 getTimeoutMS = frames/speed 随 speed 自然缩短，不再补偿
            .timeout(0)
            .setHoldAction(original::holdAction)
            .clickAction(original::clickAction)                        // 保留原版出刀 + StunManager
            .setHitEffect(original::hitEffect)
            .releaseAction(original::releaseAction);
    if (original.getLoop()) builder.loop();
    if (original.isAerial()) builder.aerial();
    return builder.build();
}
```

连段链定义：

```java
public static final DeferredHolder<ComboState, ComboState> FAST_COMBO_A1 =
        COMBO_STATES.register("combo_a1_fast", () -> fastGround(ComboStateRegistry.COMBO_A1, 3, x -> FAST_COMBO_A2.getId()));
public static final DeferredHolder<ComboState, ComboState> FAST_COMBO_A2 =
        COMBO_STATES.register("combo_a2_fast", () -> fastGround(ComboStateRegistry.COMBO_A2, 3, x -> FAST_COMBO_A3.getId()));
public static final DeferredHolder<ComboState, ComboState> FAST_COMBO_A3 =
        COMBO_STATES.register("combo_a3_fast", () -> fastA3(ComboStateRegistry.COMBO_A3, 3, x -> FAST_COMBO_A4.getId()));
public static final DeferredHolder<ComboState, ComboState> FAST_COMBO_A4 =
        COMBO_STATES.register("combo_a4_fast", () -> fastGround(ComboStateRegistry.COMBO_A4, 3, x -> FAST_COMBO_A5.getId()));
public static final DeferredHolder<ComboState, ComboState> FAST_COMBO_A5 =
        COMBO_STATES.register("combo_a5_fast", () -> fastGround(ComboStateRegistry.COMBO_A5, 3, x -> ComboStateRegistry.NONE.getId()));
```

- `branchFrames = 3` → `getTicksFromFrames(3) = 2` tick（100ms）。先保守，验证后再降到 `2`（1 tick）或 `1`（0 tick）。
- `FastComboBridge` 保留：它负责"首次进入 A1 时把 `combo_a1` 换成 `combo_a1_fast`"。之后 A1_fast→A2_fast→… 已自闭环，桥不会再介入（`combo_aN_fast` 不在映射表里，自然 no-op）。

**A3/A4/A5 的 tick 命中需要单独重排**（`fastGround` 的 `setTickAction` 仍委托原版，等于没动）：

```java
// A3 fast：原 2/6 tick → 1/2 tick
.addTickAction(ComboState.TimeLineTickAction.getBuilder()
        .put(1, e -> AttackManager.doSlash(e, -61.0F, false, false, 0.44F))
        .put(2, e -> AttackManager.doSlash(e, 138.0F, false, false, 0.44F))
        .build())
```

A4（原 8/9 → 2/3）、A5（原 15/17/19 → 2/3/4）同理，保持"动画与判定同步"。

> 注：A1/A2 的伤害在 `clickAction`（进入即出刀），没有 tick 偏移，改分支窗口即可提速；A3/A4/A5 是终结段，多段伤害在 tick 时间轴上，必须单独重排。

### 阶段三：验证与验收

1. 对比朝露（原版连段）与初雪（fast 连段）A1→A2→A3 的 `elapsedTick`，初雪应明显更短。
2. 动画与伤害判定同步（不再"刀过去了伤害才来"）。
3. 连续右键能正常推进 A1→A2→A3→A4→A5。
4. 长按右键仍能正常触发 SA「霜刃」（`FROST_BLADE` 状态独立，不受本次改动影响）。
5. GameTest 全绿（现有 `gametest-0.1.2-*.log` 覆盖的伤害/判定用例不回归）。

## 3. 建议初始参数

| 参数 | 原版 | 初雪建议（先保守） | 后续 |
|---|---|---|---|
| 连段 `speed` | 1.0 | 1.5× | 1.75× / 2.0× |
| A1/A2 分支窗口 | 5 帧 = 3 tick | 3 帧 = 2 tick | 2 帧 = 1 tick |
| A3 分支窗口 | 9 帧 = 6 tick | 3 帧 = 2 tick | 2 帧 = 1 tick |
| A4/A5 分支窗口 | 21/33 帧 | 3 帧 = 2 tick | — |
| `timeout` 字段 | 0 | 0（随 speed 自然缩短） | — |
| `ATTACK_SPEED` 额外加成 | — | 0（移除） | — |
| 连段数量 | A1–A5 | 保持 A1–A5 | — |
| 连段伤害 | — | 保持初雪现有设计 | — |
| SA「霜刃」 | — | **独立**，不随连段倍率改 | — |

霜刃七段在 `FROST_FIRST_TICK=4, FROST_INTERVAL=2`（第 4/6/8/10/12/14/16 tick）触发，属于 SA，与普通连段加速无关，**保持不动**。

## 6. 相关观察（可选，不在本次范围）

`MistletoeBlade.BLADE_KEYS` 只含 `mistletoe` 与 `dawn`，**不含 `first_snow`**，因此 `isMistletoe(first_snow)` 返回 `false`。当前多处（`canFight`、`MistletoeDamage` 的直击分支）靠这个"意外"让初雪不走暮色生命差公式。建议后续把初雪判断显式化（例如新增 `isMistletoeOrFirstSnow`），避免未来改动时踩坑。

## 7. 实施结果（2026-11-09）

已按本方案实施，产物 `dist/mistletoe-0.1.2.jar`（已同步到 PCL / Axolotl 两个整合包的 `mods/`）。

- 阶段一：`FirstSnowSpeedHandler`、`LivingEntityHurtMixin`、`MistletoeAutoAttack`、`FirstSnowHoldPayload`、`FirstSnowHoldScheduler` 已删除；`TerminalBlade` 的 payload 注册、`mistletoe.mixins.json` 的 mixin 条目、`MistletoeDamage` 的初雪 i-frame 兜底与 `FIRST_SNOW_IFRAME_TARGETS` 全部清理。
- 阶段二：`ModComboStates.fastGround` 改为固定 6 段自闭环链 A1→A2→A3→A4→A4_EX→A5→A1；分支窗口按「最后一段命中 + 1 tick」取（A1/A2=3 帧、A3=9、A4=15、A4_EX=23、A5=30）；`speed=1.0`，命中 tick 与动作保持原版（2.0.7 玩家 VMD 动画无法变速）。
- 验证：JUnit 12/12；GameTest 29/29（含 T-20 初雪 fast combo 重定向、以及贴脸低头 `frostBladeHitsPointBlankWhenLookingDown`），日志 `run-gametest/gametest-revert.log`。
- 追加修复：霜刃扇形由「眼睛→眼睛 3D 向量」改为**水平扇形**，贴脸时目标不再被眼睛高度差推出 100° 锥角。
- 追加修复（动作异常）：快速连段在客户端补注册玩家 VMD 动画。SlashBlade 的 `PlayerAnimationOverrider` 动画表只注册了 `slashblade:combo_a1..a5`，重定向到 `mistletoe:combo_aN_fast` 后查不到动作，玩家会退化成原版挥臂；现按原版帧区间补齐（反射兼容 2.0.7 / 2.1.9 两种表结构）。
- 追加修复（第 6 段）：原版 A 有 6 个地面招式（A1/A2/A3/A4/A4_EX/A5），fast 链把 A4_EX 串在 A4 之后，补了 `combo_a4_ex_fast` 的玩家动画（800-894 帧），GameTest `fastComboChainHasSixStages` 校验整条链路。
- 追加修复（动画跟不上）：2.0.7 的玩家 VMD 动画（`VmdAnimation`）每 tick 固定 `currentTick++`、没有 speed 字段，无法安全变速。试过 `FastVmdAnimation` 子类（重写 `tick()` 加速），但它按 2.1.9 编译会生成返回 `PlayerAnimationBase` 的桥接方法，2.0.7 没有这个类导致加载失败，已回退。最终把命中 tick 和 speed 恢复原版，只压缩换段窗口（按“最后一段命中 + 1”取），保证动画和伤害对齐。
- 追加修复（动画跟不上）：2.0.7 的玩家 VMD 动画（`VmdAnimation`）每 tick 固定 `currentTick++`、没有 speed 字段，永远 1.0x。之前把 `speed` 拉到 1.5x 并把 A3/A4/A4_EX/A5 的命中 tick 前移，导致伤害先于身体动作出现。现改为**命中 tick 和 speed 都保持原版**，只压缩换段窗口（按“最后一段命中 +1 tick”取），并保留 A1/A2 的 2-tick 快速起手。
- 待游戏内手感确认：1.5x 是否够快、A4/A5 命中前移后视觉是否可接受；不满意可调 `FAST_GROUND_SPEED`（1.5/1.75/2.0）与 `branchFrames`。
